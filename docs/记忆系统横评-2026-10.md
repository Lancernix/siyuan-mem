# 记忆系统横评：为什么这一类工具用起来都「一般般」

2026-10-28。数据全部来自第三方独立测试和公开论文，不是厂商页面。

---

## 一、一句话结论

不是你用得不对，是这一整类现在就到这个水平。**做得最好的系统，在第三方测试里答对率也只有 57.6%，没有一家接近自己宣传的数字。**

---

## 二、硬数据：五个系统跑同一段对话

2026 年 9 月的独立测试。同一段 419 轮对话、120 个问题、同一个答题模型（gpt-4o-mini，temperature 0）、每个系统都取 top 10 结果。**每个系统只按它检索回来的文本打分，答题模型不能用自己的知识补。**

| 系统 | 答对率 | 正确拒答 | 搜索 p50 | 每次上下文 token | 每轮写入耗时 |
|---|---|---|---|---|---|
| GoodMem（厂商调优配置） | 57.6% | 82.1% | 754 ms | 504 | 0.28 s |
| GoodMem（默认配置） | 53.3% | 92.9% | 633 ms | 503 | 0.28 s |
| Letta 0.11.7 | 52.2% | 92.9% | 318 ms | 503 | 0.37 s |
| Mem0 2.1.0 | 50.0% | 92.9% | 38 ms | 353 | 1.52 s |
| LangMem 0.0.30 | 45.7% | 85.7% | 68 ms | 884 | 4.15 s |
| Zep / Graphiti 0.30.2 | **37.0%** | 92.9% | 163 ms | **212** | 3.65 s |

厂商自报的数字：Mem0 宣称 LoCoMo 92.5%，Zep 宣称 83%。独立测出来是 50% 和 37%。

Zep 在纯召回上垫底，但它返回的上下文最少（212 token），所以选它的理由是"省 token 省得最多"，不是"记得最准"。

## 三、病在哪：三种，都能对上你的体感

### 1. 粒度错了 —— 你说"记了很多碎的"，就是这条

把每条消息、每个小结论都当独立记忆存进库，向量库里全是低信息密度的碎片：寒暄、一句同意、随手一问。

后果不只是检索变慢。有实测观察：**当记忆被这种碎片灌满时，模型的输出本身会变得平庸**——话变短、变泛、技术含量下降，像是在模仿那个低信噪比的库。这叫 coherence tax（连贯性税），从检索问题升级成了生成问题。

正确的单位是**一个话题一段**，不是**一条事实一行**。

### 2. 只靠语义相似度召回

典型翻车场景：用户说"今天又被领导批评了，心情很差"。系统按相似度召回，把三个月前那句"我领导养了只很可爱的猫"也拉了进来，回复变成"不过你领导那只猫今天有没有安慰到你"。

"领导"和"批评"在向量空间里跟"领导"和"猫"是一样近的。语义相似不等于语境相关。

修法不是换更好的 embedding，是**先用结构化条件把候选砍掉再排序**：实体、类型、时间、是否失效。纯向量 top-k 是所有失败模式里最笨的一种。

### 3. 幽灵记忆（ghost memory）—— 这条最隐蔽，也最伤

失败不是"忘了"，是**记得太多版本**。旧的、新的、过渡期的三套事实同时在库里，语义高度相似，一起被召回，模型很自信地综合出一个错的答案。

给现有系统加一层"状态标注"（当前 / 历史 / 过渡），实测能把冲突判断准确率提升 0.240（绝对值），时序 F1 从 0.030 提到 0.171。**光加时间戳没用，光加相关度排序也没用**，必须显式标失效。

## 四、反主流的一条证据：抽取本身就是丢信息

现在主流的做法都是"LLM 在门口判断什么值得记，抽成事实存下来"。这个思路有个信息论上的硬伤：**抽取是不可逆的有损压缩**。

写的时候 LLM 觉得"用户偏好 PostgreSQL"值得记，于是存了这条。三个月后你问"我上次折腾的那个数据库是啥"，cue 对不上，答案在写的那一刻就被扔了，任何 embedding 模型都救不回来。

实测数据（同一批基准）：

- **不做 LLM 抽取、原文本直接进向量库**：LongMemEval-S 上 R@5 到 **96.6%**，加一个 rerank 到 **99.4%**
- 同一个难度更高的测试（ConvoMem）：原文直存 **92.9%**，Mem0 各分类只有 **30-45%**

原文直存，零抽取，打赢了精心设计的抽取管线。

### 但这不等于"什么都存"

原文直存的问题正是你遇到的噪音。所以真正的解法不是二选一，是：

> **原文不动，写入时只打标签；召回时先按标签过滤，再排序。**

抽取的不是"内容"，是"元数据"。内容一个字都不丢，所以不会出现"当初扔掉了、后来查不到"；元数据负责把噪音挡在召回之外。

## 五、落到思源上的四条规则

### 规则一：单位是一个话题一段

不是一条事实一行。判断标准：这段话单独拿出来，能不能让人看懂在说什么。看不懂就是切碎了。

### 规则二：原文进块，标签进属性

块里放原始对话片段（可以摘录，但不要改写成结论）。属性里放：

- 实体（投影仪桌面 / 风盾500 / DSH 插件）
- 类型（决策 / 偏好 / 事实 / 教训 / 待办）
- 置信度（用户明确说的 5，推断的 2）
- 来源（会话 id + 日期）
- 取代了哪条
- 状态（当前 / 历史 / 已废弃）

### 规则三：召回先过滤再排序

```
WHERE 实体 IN (...) OR 类型 IN (...)
  AND 状态 = '当前'
  AND 置信度 >= 3
ORDER BY 相关度 × 置信度 × 衰减分
LIMIT N
```

不是全库 top-k。这一步就把"领导养猫"那类噪音挡在门外了。

### 规则四：新条目取代旧条目时，旧条目标失效

不要平行新增一条。否则三条平行记忆最后就是幽灵记忆。宁可让历史条目留个"已被 xxx 取代"的引用，让它可查但不默认注入。

## 六、什么时候才需要上向量检索

v1 不需要。先用：实体过滤 + 思源全文检索 + 标题/文档名匹配。

跑两周，记录**哪些查询没命中**。如果漏掉的大多是"意思对但词不对"，那才上向量；如果漏掉的是"根本没记过"，那是写入策略的问题，上向量也没用。

判断方法很简单：把没命中的查询列出来，人工看一眼答案在不在库里。

- 在库里但没搜到 → 检索问题，上向量
- 不在库里 → 写入问题，改抽取规则

## 七、这套东西的现状总结

| | 状态 |
|---|---|
| 存储层 | 成熟，随便选（向量库、图库、SQLite 都行） |
| 抽取层 | **不成熟**，"什么值得记"是领域判断，模型给不了 |
| 召回层 | 半成熟，纯向量不行，过滤+重排能用 |
| 遗忘层 | **基本空白**。有测试显示图结构系统在对抗性遗忘测试里只有 4.4-7.0% 得分 |

最后一行值得单独说：**召回和删除是两个不同的器官。** 整个行业在测召回，然后在实际使用里栽在"删不掉、失效不了"上。

---

## 八、给这个领域的判断

两年内不会有开箱即用的好方案，因为核心难题是"什么值得记"——这是领域判断，不是模型能力。凡是号称自动解决的，都会退化成"记得很多、都记不准"。

反过来，**你自己做有天然优势**：

1. 只有一个用户，偏好稳定，不需要处理多租户
2. 只有一个领域，可以手写规则决定什么该记
3. 存储就在你每天读的思源里，写错了你会看见

这三条是商业产品做不了的。所以别等工具，自己搭。
