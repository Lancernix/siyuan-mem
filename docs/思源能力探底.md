# 思源能力探底

> 2026-10-30 凌晨实测。全部在临时笔记本 `99-能力测试` 里做，不碰正式库。
> 目的：把「思源能做什么」从猜测变成实测，避免设计完发现做不了再返工。

写这份文档的直接原因：在 `mem` 的实现里，因为没摸清下面这些，返工了五轮——实体表读成空、分组写出 54 个重复标题、同一段原文传两遍、建出三个同名文档。每轮都要重跑 96 秒的抽取 + 清库。

---

## 一、块模型：谁能装东西，谁不能

这是最影响结构的结论。**标题和段落都是叶子块，不能有子块。**

| 块 | type | 能当容器 | 说明 |
|---|---|---|---|
| 文档 | `d` | ✅ | |
| 标题 | `h` | ❌ | `heading is a leaf block and cannot have children` |
| 段落 | `p` | ❌ | `block type "p" is a leaf block` |
| 列表块 | `l` | ✅ | 子块是列表项 `i` |
| 列表项 | `i` | ✅ | 子块是段落 `p` |
| 引述块 | `b` | ✅ | |
| 超级块 | `s` | ✅ | markdown 语法 `{{{\n…\n}}}` |

**推论**：

1. **不能用标题分组。** 想「在 `## 2026-10-29 · MiniWMS` 下面挂条目」是做不到的——标题是叶子块。只能把条目用 `previousID` 插在标题后面，但那样它就落在文档顶层，不属于任何组。
2. **正确做法是列表或超级块。**
   - 列表：`- 2026-10-29 · MiniWMS` → 子列表项 → 段落。视觉上就是「话题 + 下面的点」，正是记忆想要的结构。
   - 超级块：一组块外面套个框，适合当一个「卡片」。
3. **`appendBlock(docId)` 不会报错但行为要注意**：它把块追加到文档末尾；如果文档末尾是标题，新块的 `parent_id` 会记成那个标题（SQL 里看着像"标题的子块"，实际渲染是同级）。**不要用 `parent_id = docId` 来查文档内容**，会漏。要按 `box`（笔记本）或 `path LIKE` 查。

## 二、SQL 索引是异步的，延迟约 3 秒

实测：`appendBlock` 返回后轮询 `SELECT id FROM blocks WHERE id='…'`，**2896ms** 后才可见。

**推论**：

1. **任何「写完立刻查」的代码都是错的**。我们的幂等判断（这段原文是不是已经归档过）、实体表读取、块存活检查，全都踩过这个坑。
2. 正确做法：**本地记一份权威索引**（`raw-index.json`、`entry-groups.json`、`entity-negatives.json`），SQL 只在本地丢了时兜底。
3. 清空文档时要**循环删 + 等**，一次删不干净（实测第一遍删完还剩 10 条）。

## 三、渲染：支持什么

`appendBlock(dataType="markdown")` 全部实测通过，块类型如下：

| 语法 | 建出来的块 type | 说明 |
|---|---|---|
| 表格 | `t` | |
| 任务列表 | `l` + subtype `t` | `- [ ]` / `- [X]`（`[x]` 会被存成大写 `X`） |
| 块引用 `((id "锚文本"))` | `p` | 锚文本可自定义，与块内容无关 |
| 公式 `$$…$$` | `m` | |
| 代码块 | `c` | |
| mermaid | `c` | 代码块的一种，渲染成图 |
| 内联 HTML | `html` | `<div style="color:red">` 会被渲染 |
| 脚注 | `p` | `正文[^1]` + `[^1]: 内容` |
| 高亮 | `p` | `==高亮==` |
| 标签 | `p` | `#标签/测试#` |

**推论**：文本之外的表现力足够。表格、公式、mermaid 都能直接用，不需要额外机制。图表（ECharts 之类）没测，但我们暂时用不上。

## 四、附件引用：放正文里就算「被引用」

- 附件上传到 `data/assets/<子目录>/`，内核会自动改名（加时间戳 + 随机后缀），**返回路径必须存下来**。
- `GET /assets/xxx.jsonl` 能直接取回，二进制一致。
- **块正文里出现该路径的链接，这个附件就不会被「清理未引用资源」带走**（实测 `siyuan asset unused` 里查不到它）。
- 只放在块属性里也查不到，但属性不参与检索，**不能作为保活的依据**（未验证：属性是否真的算引用；为安全起见按「不算」处理）。

**推论**：原文不再需要 `02-原文` 这个「保活文档」。**在每个 part 对应的第一条记忆正文里放一个链接**就够——一个 part 只要被引用一次就保活。

---

## 五、文档内容不能整体替换

- `createDocWithMd` 传**已存在的 path**：**新建一份**，不是覆盖。实测一次就建出三个同名 `/06-记忆摘要`。
- 想靠「删块再写」绕开：块索引延迟 3 秒，刚建完查不到子块，于是「删了个空、又追加一份」，跑两次就有两份内容。
- `removeDocByID` 返回 `code:0` 之后，SQL 里还要几秒才消失；紧接着按同名建会建出重复。

**推论**：**派生视图不要写成思源文档**。要么用 AV 视图（见下），要么只在终端输出。

## 六、属性视图（AV / 数据库）：能建、能改、能自动维护

2026-10-30 修正。上一版这里写的是「能改不能建」，**结论是错的**——错在只翻了 `/api/av/*`
和 CLI，没去看前端到底走哪个口子。

### 正确的建法

```
1) POST /api/block/insertBlock   dataType:"dom"
   data: '<div class="av" data-node-id="<ID>" data-av-id="<ID>"
                data-type="NodeAttributeView" data-av-type="table">
            <div spellcheck="true"></div>
            <div class="protyle-attr" contenteditable="false"></div>
          </div>'
   parentID: <文档id>
   → 得到一个 type='av' 的块，但 getAttributeView 仍是 {av:null}

2) POST /api/av/renderAttributeView {id:"<ID>", blockID:"<ID>", viewID:"", page:1, pageSize:20}
   → 内核把空壳落成真的 av 文件：默认「表格」布局 + 主键(type=block) 列
   → 返回里带 viewID，后面所有事务都要它
```

关键是第 2 步：**渲染一次就等于初始化**。之前卡在「插了块怎么还是 null」，就是没调它。

### 之后全部走 `/api/transactions`

前端加列、加行、写单元格走的是这个通用事务接口，不是 `/api/av/*`：

```jsonc
POST /api/transactions
{ "reqId": 1793360941572,          // 必填，漏了报 "Field [reqId] is required"
  "transactions": [{ "doOperations": [ ... ], "undoOperations": [] }] }
```

用到的 action：

| action | 作用 | 关键字段 |
|---|---|---|
| `addAttrViewCol` | 加列 | `avID, blockID, viewID, id, type, name`（type：text/number/date/select/block…） |
| `removeAttrViewCol` | 删列 | `avID, blockID, viewID, id` |
| `insertAttrViewBlock` | 加行 | `avID, blockID, viewID, previousID, groupID, srcs:[{itemID, id, isDetached}]` |
| `updateAttrViewCell` | 写单元格 | `id, avID, keyID, rowID, data:{type, …}` |
| `sortAttrViewCol` | 调列序 | `avID, blockID, id, previousID` |
| `setAttrViewName` / `setAttrViewViewName` | 改名 | `id`（avID 或 viewID）, `data` |

行绑定已有块：`srcs: [{itemID: <新id>, id: <已有块id>, isDetached: false}]`——这一条就是
「把一批块加进数据库」。`itemID` 是行 id，也是后面 `updateAttrViewCell` 要的 `rowID`。
脱离块的空行用 `isDetached: true` + 自造 id。

单元格的值形状（写进去再读回来一致，实测）：

```jsonc
{ "type": "text",   "text":   { "content": "mcp-adapter" } }
{ "type": "number", "number": { "isNotEmpty": true, "content": 4 } }
{ "type": "date",   "date":   { "isNotEmpty": true, "content": 1793332800000,
                                "content2": 0, "hasEndDate": false, "isNotTime": true } }
```

### 和 CLI 的关系

CLI 的 `database` 子命令确实没有 create，但它只是这套 REST 的一层壳，能建的是事务层。
Docker 部署下 CLI 也只能在容器里跑（`docker exec -it siyuan siyuan … -w /siyuan/workspace`），
宿主机不该直接改 workspace。

### 实测结果

`zz-条目表` 里建了一张：12 条真实条目绑成行，列是 主键(block) / 话题 / 摘要 / 类型 / 置信度 /
日期，渲染正常，点主键能跳回原条目块。整条链路只用了 REST，没有人工点过一次。

所以 AV 从「人工建一次」升级成「程序化建 + 程序化维护」。要不要把它当主视图另说，
但能力上不再有缺口。

## 七、第二轮：嵌入块、超级块、资源引用

### 嵌入块 `{{select …}}` —— 动态视图，不用重建文档

写一句 markdown 就得到一个块（`type=query_embed`），内容是裸 SQL：

```
{{select content, ial from blocks where box='<笔记本id>' and ial like '%custom-mem-entity%' limit 10}}
```

**渲染由前端做**：后端 `getBlockDOM` 只返回壳（`data-content` 里挂着那句 SQL），
打开文档时前端执行查询、渲染成表格。所以程序侧只需要写对 SQL，不需要管渲染。

这条解决了一个具体问题：之前想给「记忆摘要」做一个派生视图，得删块重写，
而块的 SQL 索引有 3 秒延迟、`createDocWithMd` 又不覆盖同 path，踩了三个坑
（建出三份同名文档、跑两次有两份内容）。嵌入块是**查询**不是快照，
数据变它就变，永远不会不一致。

局限：渲染出来是表格，固定样式。适合「最近条目」「某个话题下的全部条目」这种
平铺视图，不适合要层级感的结构。

### 超级块能建，引述块不能（用这个语法）

- `{{{row … }}}` → `type=s`，可以当容器（横向分栏）。
- `> 引述文字` 这种 markdown 建不出 `type=b` 的块（可能要走别的语法）。

### 属性里的资源路径**不算**被引用

实测：上传两个文件，一个路径只写进块属性 `custom-probe-asset`，另一个写进正文
`[链接](assets/…)`。结果前者出现在「未引用资源」列表里，后者不在。

**所以原文链接必须挂在正文**。我们的 `custom-mem-raw` 属性里也存了
`assets/…#120-180`，那只是个指针，不承担保活；保活靠条目分组项里的那个
`[原文](…)` 链接。

### 列表项 append 得到的是**同级**列表项

`appendBlock(parentID=列表项)` 不会产生子项，而是同一层级的下一项。
所以「话题 + 条目」是一个平铺列表，话题那条加粗当视觉分隔——渲染上就是
「一条加粗标题 + 下面几条」，够用。实测 02-实体 的块结构：
11 个 `l`（列表块）/ 60 个 `i`（列表项）/ 1 个 `h1`，缩进 2 空格。

### 还没验证

- 跨笔记本的块引用（试了一次没渲染出来，可能本来就不支持）
- AV 绑定已有块（`addAttributeViewBlocks` + `isDetached:false`）——要人工建一张表才能试
- 模板、挂件
