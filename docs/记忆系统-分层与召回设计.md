# 记忆系统：分层、标签、取代、召回

2026-10-28。接在《思源作为DSH记忆后端-设计》和《记忆系统横评》之后，回答具体实现问题。

本机实测环境：思源 301 篇文档 / 41322 个块。

---

## 一、全量会话要不要存

**要，但它是原料层，不是召回目标。**

理由：抽取一定丢东西，丢了就永久丢了。原文是唯一能把丢掉的东西找回来的地方。

但原文**不能进默认召回**，否则就是你说的那种噪音爆炸。所以做法是：

| 层 | 存什么 | 参与默认召回 | 用途 |
|---|---|---|---|
| 原文层 | 会话逐轮原文，一段一块 | 否 | 回溯、重新抽取、查"当时到底怎么说的" |
| 段落层 | 一个话题一段，通常是 3-20 轮 | 是 | 默认召回目标 |
| 条目层 | 关键决策/偏好/教训，一条一句 | 是 | 高置信注入 |

这是**多分辨率索引**：段落层回答"我们怎么定的"，原文层回答"他原话是怎么说的"。只有一个分辨率，总有一类问题检索不到。

存储成本可以忽略：一天两万字，一年七百万字，纯文本约 20MB。25G 硬盘上这不是问题。

**原文层要按月归档**（一个文档一个月），否则一个文档几千块，思源渲染会卡。

## 二、thinking 块算不算

**原文归档：算，但单独存、不进搜索索引。**
**记忆抽取：不算。**

thinking 里大部分是被否定的方案。你自己举的 Oracle 例子就是典型：如果他推理时写了三十行"Oracle 也行、MySQL 也行、要不 Oracle 吧"，抽出来就是三条平行记忆，后来选了 MySQL，那两条还在，召回时一起冒出来。

但 thinking 是"理由"的唯一来源。所以规则是：

> 抽取时**不把 thinking 当事实来源**，只当**理由来源**，而且写入时必须标注"这是当时的推理，未经确认"。

实现上给条目加一个字段 `依据=推理 / 依据=用户明说`，两者在召回里权重不同。

还有个现实原因：thinking 通常是输出的三到五倍长。索引它等于把库的信噪比直接砍到四分之一。

## 三、打多少标签

**四个必填，两个可选。多一个都别加。**

必填：

| 字段 | 取值 | 为什么必填 |
|---|---|---|
| 实体 | 一句话，如 `投影仪桌面` / `风盾500` | 去重和过滤的主键 |
| 类型 | 决策 / 偏好 / 事实 / 教训 / 待办 | 决定注入方式和权重 |
| 状态 | current / superseded / archived | 挡幽灵记忆，没有它整套就废 |
| 日期 | YYYY-MM-DD | 模型会把无日期的记忆当恒真 |

可选：

| 字段 | 说明 |
|---|---|
| 取代 | 指向被取代的块 id |
| 依据 | 用户明说 / 推理推断 |

**明确不要打的两类：**

**情感标签。** 有些方案会给记忆打"愤怒、焦虑、职场压力"。对个人知识库没用，而且这类标签靠模型判断，同一条内容换个模型就打不一样。

**重要性评分。** 让模型在写的时候打 1-10，这个数不可校准——它不知道自己以后会不会用到。**重要性应该由使用行为算出来：被召回几次、被引用几次。** 写的时候打分是拍脑袋，用出来才是真的。

标签多了的代价是实打实的：每写一条都要多判断一次，写入变慢，而且大部分字段长期空着。四个字段够用。

## 四、新事实替代旧事实：删、归档、还是标过时

**标 superseded。不删。**

三态设计：

```
current     —— 当前有效，参与默认召回
superseded  —— 被取代，不参与默认召回，但可查
archived    —— 归档（话题结束、项目下线），不参与召回
```

取代的动作是两步，都要做：

1. 新条目写 `取代 = <旧块 id>`
2. 旧条目 `状态 = superseded`，写 `被取代于 = <新块 id>`

**为什么不删：**

时间本身是记忆的一个维度。"以前这么做，后来有更好的方案"——这个变化过程是有价值的。你以后问"为什么现在不用 Oracle 了"，答案就在被取代的那条里。删了就答不出来。

而且删是不可逆的。抽取本来就有损，再叠一层删除，最后什么都找不回来。

**唯一该硬删的三种情况：**

1. **提取错误** —— 记的根本不是事实，是模型幻觉
2. **隐私敏感** —— 密码、证件号、别人的私事
3. **完全重复** —— 逐字一样的第二次写入（这个应该在写入时就拦住，不是靠事后删）

其余一律标状态。

## 五、思源查得快不快 —— 实测

本机 301 篇文档、41322 个块，实测：

| 操作 | 耗时 |
|---|---|
| SQL `count(*)` | 1.0 ms |
| SQL 带 `LIKE` 条件 | 2.1 ms |
| 全文搜索单词（76 命中） | 11.8 ms |
| 全文搜索单词（另一词） | 19.7 ms |
| 全文搜索 6 个词的长句 | 21.1 ms，**0 命中** |

**结论：快得离谱。** 1-20 毫秒这个量级，意味着可以**每条消息进来都查一次**，甚至查十次都没感觉。这直接推翻了很多"为了性能只能偶尔召回"的设计顾虑。

**但有个坑必须记住：思源的全文搜索是关键词 AND，不是语义。**

验证：搜"记忆"命中 76 条，搜"记忆 笔记"只剩 5 条，搜"投影仪桌面启动器焦点动画主色"直接归零。

所以**不能把用户原话丢进去搜**，必须先抽关键词，或者用 SQL 逐词 OR。这是实现时第一个会踩的坑，而且它不报错，只是安静地返回 0。

## 六、怎么分层

四层，按**变动频率**分，不按重要性分。

| 层 | 内容 | 注入时机 | 预算 | 变动频率 |
|---|---|---|---|---|
| **L0 常驻** | 人格、硬偏好、当前项目 | system prompt | 600-800 字 | 一个月 |
| **L1 会话级** | 当前项目相关 5-10 条 | 会话开始 | 800 字 | 每次会话 |
| **L2 机会级** | 命中实体时 1-3 条 | 关键词触发 | 200 字/次 | 每轮可能 |
| **L3 按需** | agent 主动查 | 工具调用 | 无硬上限 | 随时 |

**核心原则：低速层稳定，高速层灵活。层搞反了，模型行为就会漂移。** 如果人格和偏好放在 L1 每次随机召回，你会觉得这个助手"每天性格不一样"。

### L0 常驻层

**手写，不由模型生成。**

内容就是你现在 USER.md / SOUL.md 那套：怎么称呼、语气偏好、时区、正在做的项目、明确的禁区。

为什么手写：这层决定每次对话的基调。让模型自动生成，它会把自己上一次的回答总结成"用户喜欢这样"，越滚越偏，几周后变成一个你没见过的说话风格。

### L1 会话级

会话开始时，按当前工作目录 → 找到对应项目 → SQL 过滤 → 打分 → 取 5-10 条。

打分：`置信度 × 衰减分`，同类里按日期新到旧。

注入位置：第一条用户消息附近，**不要塞进 system prompt**。system prompt 里的东西模型会当规则，这里的东西是背景。

### L2 机会级

维护一张**实体词表**：所有实体的名字（投影仪桌面、风盾500、DSH、思源、Next Player…）。

每条用户消息进来，先做一次字符串匹配（毫秒级，不用模型），命中的实体才去查。**不要每轮跑 embedding。**

没有命中就什么都不做。绝大多数对话轮次不该触发召回。

### L3 按需

给 agent 一个 `memory_search` 工具，描述写清楚：什么时候该用、返回什么、怎么用。

**这一层被严重低估。** 行业都在做自动注入，但自动注入只能覆盖"你猜它会问的"；给一个工具，它能覆盖真实需要。

我的判断：预算应该反过来分——L1 给少一点，L3 的能力做扎实。宁可少注入、让它主动查。

## 七、注入的硬规则

**每条注入必须带三样：日期、来源（哪次会话）、状态。**

不带日期的记忆，模型会当恒真。带了日期它才知道"这是三个月前的，可能已经改了"。

**预算必须硬性截断，不能"差不多"。** 没有预算控制的记忆系统会慢慢吃掉整个上下文窗口，而且你察觉不到，只会觉得模型变笨了。

**注入格式用结构化列表，不要用散文。** 散文式记忆会诱导模型复述，结构化列表它才会当参考。

## 八、落地顺序

不要一次做完四层。按这个顺序：

1. **L0 手写** —— 半天。收益最大、风险最低。
2. **写入侧** —— 会话结束抽 3-8 条，去重合并，写进思源独立笔记本。这是工作量最大的一块。
3. **L3 工具** —— 一个 search 函数 + 一段好的工具描述。比 L1 简单，效果比 L1 好。
4. **L1 会话级** —— 有了稳定数据再做，否则召回的都是早期垃圾。
5. **L2 机会级** —— 最后做。它是优化，不是必需。

**先做 L1 是最常见的错误。** 库里没有干净数据的时候做自动召回，召回的全是噪音，你会以为是算法问题，其实是数据问题。

## 九、还悬着的问题

- **衰减怎么算**：按时间线性还是有使用加成？我倾向"被召回一次抵 30 天"，但需要跑一段时间看数据。
- **跨项目实体怎么处理**：`思源` 在写文章和做记忆系统里都出现，是两条还是一条？倾向一条，靠类型区分。
- **会话中途改主意怎么办**：这一轮说"用 A"，下一轮说"还是 B 吧"。是立即写 superseded，还是等会话结束统一处理？倾向等会话结束——中途改主意有一半会再改回来。
- **谁来判断"这条值得记"**：现在倾向规则 + 模型混合。纯规则漏，纯模型吵。这个比例要试。

## 十、记录边界（修订前一节的判断）

前一节我说 thinking 归档但不上索引。**这个判断收回，改成一刀切：thinking 不记，工具调用也不记。**

只记两样：**用户的输入，模型的最终输出。**

理由：

**thinking 不可复用。** 它记的是当时的犹豫和试错，而环境已经变了。事后回看"当时考虑过 Oracle 但排除了"，除了制造噪音没有任何用途——因为排除的理由最终要么进了输出，要么本来就是错的。

**工具调用的结果在磁盘上。** 命令跑完，文件就在那儿；接口调完，数据就在那儿。记忆库再记一遍"我执行了 git commit"，是重复。真正需要记住的是"为什么改"，那个在输出里。

**过程不能当证据。** 一个 agent 干了二十步才成功，二十步的过程不值得存；值得存的是"这么做能成"。过程的每一步都依赖当时的环境，换个时间就失效。

**唯一的代价**：出了问题时没法复盘"当时它到底想了什么"。这个需求是调试需求，不是记忆需求，应该靠日志解决，不要混进知识库。

所以原文层的单位明确为：**一问一答**。带时间戳、会话 id、轮次号。没有中间过程。

## 十一、写进思源用什么格式：Markdown 进，SQL 出

这两个不是二选一，是分工。

**写入用 Markdown。** 调 `createDocWithMd`（整篇）或 `appendBlock`（追加块），传 md 文本，思源自己解析成块、建索引、生成块 id。

**标签用块属性。** 调 `setBlockAttrs` 挂 `custom-*` 字段。**不要把标签塞进正文**，否则它会进全文索引，污染搜索结果，而且以后改标签要动正文。

**查询用 SQL。** 但注意——

> **思源的 SQL 接口是只读的，而且是静默失败。**

实测：发一条 `UPDATE blocks SET content='x' WHERE id=...`，接口返回 `{"code":0,"msg":""}`，看起来成功，实际什么都没改。`CREATE TABLE` 同样返回 code 0。不报错、不提示、不生效。

这个坑比报错严重得多：写错一次你不会知道，要等下次查询发现数据没变。

**绝对不要直接改数据目录里的 `.sy` 文件。** 那是块级 JSON 树，绕过 kernel 写会破坏索引，块 id 会漂，引用会断。思源不是 Obsidian。

## 十二、检索精度：别拿它"搜"，拿它"筛"

你担心的"搜 10 条只有 1 条有用"，这是关键词检索的固有水平，不是思源的问题，也不是 bug。换任何系统都一样。

但**实际使用里，七成以上的查询根本不需要模糊搜索**。

### 三类查询，分别处理

**第一类：查某个东西的当前状态（占大多数）**

"投影仪桌面现在什么配置"、"风盾500 最后选了哪条"。

这类**不需要搜索**，直接结构化查询：

```sql
SELECT * FROM blocks
WHERE 实体 = '投影仪桌面' AND 状态 = 'current'
ORDER BY 日期 DESC LIMIT 3
```

准确率接近 100%，因为是精确匹配，不存在"像不像"的问题。

**第二类：查演变过程**

"为什么不用 Oracle 了"、"之前那版为什么放弃"。

查 `状态 = 'superseded'` 的条目，按时间排。也是精确查询。

**第三类：真的想不起来叫什么**

"我上次聊过一个关于颜色的东西"。

这类才需要全文搜索，precision 天然低，但人可以扫一眼。而且这类的容错本来就高——你也不知道自己要找什么。

### 兜底：注入"最近变更"

会话开始不要只注入"跟这句话相关的"，同时注入**最近七天变更过的五条**。

理由很实际：你打开电脑要做的事，八成跟你上周在弄的事有关。"最近变了什么"这个信号，比"字面最像什么"可靠得多，而且完全不需要相关性判断。

这一条能显著改善"召回了十条没用的"那种体感——因为它根本不是相关性召回。

### 相关性检索的最后一道闸

真要排序，也别用单一的相似度。用这个：

```
score = 实体精确命中(0/1) × 4
      + 类型匹配(0/1)     × 2
      + 置信度            × 1
      + 新鲜度            × 1
```

实体命中的权重压到最高。因为记忆检索失败的绝大多数情况，是"实体对了但排序错了"，不是"实体都没找对"。

## 十三、谁整理、花多少 token

### 结论：harness 只交作业，整理交给独立进程 + 便宜模型

三种方案对比：

| 方案 | 成本 | 问题 |
|---|---|---|
| harness 主模型当场整理 | 最贵 | 占主上下文、拖慢会话、整理逻辑和对话逻辑互相污染 |
| harness 无脑上传，服务端全权整理 | 中 | 就是 OpenViking 那条路，服务端模型自由发挥，记一堆没用的 |
| **harness 交作业，独立 worker 按规则整理** | 最低 | 需要写规则和 schema，但规则由你定 |

选第三个。具体分工：

**harness 侧（无状态，只做三件事）**
1. 会话结束，把"用户输入 + 模型输出"的问答对打包
2. 打上项目名、时间、会话 id
3. 丢进队列，立刻返回，不等结果

**worker 侧（独立进程，异步）**
1. 从队列取任务
2. 用便宜模型按**固定 schema** 填空：实体、类型、一句话结论、依据
3. 去重（按实体 + 关键词相似度）、合并、写进思源

### 关键约束：模型只填空，不判断

**"什么值得记"由规则决定，不由模型决定。**

规则示例：
- 出现了明确的选项对比 + 最终选择 → 决策
- 出现了"我不要 / 我更喜欢 / 别这样" → 偏好
- 出现了"原来是这样 / 踩坑了 / 是因为" → 教训
- 纯问候、纯确认、纯执行 → 不记

模型只负责把选中的段落**压缩成一句话**和**填实体名**。这一步它做得很好，因为它只是在概括，不是在判断。

一旦让模型判断"这段重不重要"，结果就是 OpenViking 那个样子：它觉得每段都挺重要。

### 成本

一次会话结束，输入约 2 万字的问答原文，约 3 万 token；输出 500 字以内。

按便宜档模型算（DeepSeek / Qwen 这个级别），单次成本在几分钱量级。一天五次会话，一个月十几块。

用主模型做同样的事，成本高一个数量级，而且它得把整个会话重新读一遍——主模型本来就刚读过，重复付费。

**这笔钱该花，但别花在主模型上。**

### 别在会话结束时同步跑

会话结束 → 写队列 → 立刻返回。整理慢几秒、失败重试，都不该让用户等，也不该阻塞下一次会话。

而且异步还有个好处：可以攒批。一次整理五个会话，去重效率比一个个处理高得多——同样的"风盾500 选了哪条"在五个会话里出现，一起处理才能合并成一条。

## 十四、修订后的写入链路

```
会话结束
  ↓  harness 打包问答对（无状态，不做判断）
队列
  ↓  worker 取任务
规则筛选 ──→ 命中的段落
  ↓  便宜模型：压缩成一句话 + 填实体
去重（实体 + 相似度）
  ↓
思源：createDocWithMd 写原文块 / appendBlock 写条目
      setBlockAttrs 挂 custom-* 属性
  ↓
索引（思源自己建，不用管）
```

召回侧：

```
会话开始
  ├─ L1: 结构化查询（实体 + current + 日期排序）→ 5-10 条
  └─ 兜底: 最近七天变更 → 5 条
用户提问
  ↓
  ├─ L2: 实体词表字符串匹配 → 命中才查
  └─ L3: agent 主动调 memory_search
```

## 十五、思源侧到底能做什么（查证结果）

结论先说：**触发器不能放思源。思源只管存储和展示，整理交给外部进程。**

### 思源自带的 AI：不行

它能接 OpenAI、Claude、Ollama，但作用域是**编辑器内**：选中文字润色、总结、翻译、针对当前笔记问答。

三个硬伤：

- **没有自主性**，每次都要人点
- **没有调度**，不能定时跑
- **看不到全局**——它连笔记本列表都读不到，只能看当前打开的文档

### 思源插件：也不行，但原因不一样

插件能力其实很强：完整 API 权限、能调 kernel、能读写块、能建文档。但它的运行环境是**前端 JS，生命周期绑在应用窗口上**。

SiYuan 官方 plugin-sample 文档写得很直接：**关闭独立窗口或退出思源，不会触发前端插件的生命周期钩子**。也就是说：

- 思源一关，插件就没了
- 插件的定时器只在窗口活着的时候走
- 没有后台常驻，没有守护进程

顺带一个反证：思源 3.7.0 的 Docker 版加了**内核级定时同步**，最短 10 分钟一次。这说明"内核能调度"是成立的，但官方只给同步用，不对外开放给任意任务，而且桌面版没有。

### 现有插件：有两个能借鉴，但都不解决你的问题

**siyuan-plugin-copilot**（Achuan-2，已到 v19）

思源里最接近"agent 接思源"的东西。32 个工具，覆盖 SQL 查询、块增删改、文档创建、数据库操作，还有渐进式工具描述（省 token，思路跟 Claude Skills 一样）。

最值得注意的是它的 **SOUL 工具**：让 AI 把用户偏好和资料写进一个指定文档，每次对话前加载。**这就是一个已经落地的记忆机制**——但它用一整篇文档装全部记忆，没有条目、没有状态、没有去重、没有衰减。是记忆的雏形，不是记忆系统。

**nb-assistant**

在思源内部建本地 embedding（transformers.js + onnx），做相似度检索和 RAG 问答。证明"思源里能跑本地向量"是可行的，但：建索引必须开着思源，3000 个块在那台机器上跑了约 15 分钟。

这两个的价值是**证明了边界**：思源能被 agent 完整读写，能力不是瓶颈。缺的那一层（采集、触发、整理）本来就不该在思源里做。

### 所以，不要改造思源，也不要写思源插件

写一个**独立 worker**，几十行代码，走 kernel API。三个理由：

1. **不改思源** —— 它升级、换版本、你重装，worker 都不受影响
2. **独立进程** —— 可以崩、可以重试、可以定时、可以常驻
3. **可换存储** —— 哪天想换 Obsidian，只改 worker 的写入层，逻辑不动

### 最终形态（据 DSH 官方文档修订）

查完官方文档后，这一版比原来简单：**采集不再由插件做，插件只剩注入一件事。**

```
DSH 会话日志（~/.dsh/sessions/<工作区>/<会话>/session.v4.jsonl.zstd）
  ↓  worker 直接读，解压 + 过滤
worker（Python / Node，独立进程）
  规则筛选 → 便宜模型填空 → 去重 → 写思源
       ↓
思源（存储 + 展示 + 手动纠错）
  kernel API 写入，SQL 读出
       ↑
DSH 插件（60-80 行）
  agent/pre-step 查思源 → 注入 5-10 条 → 完
```

**为什么采集改成读日志：** DSH 的会话是 append-only 事件日志，官方架构文档明确写"模型看到的一切都必须能从日志重建"——系统提示、思考、工具调用与结果、上下文注入，全在里面。插件截获会漏、会崩、会丢；日志不会。

插件因此缩到最小：只做召回注入，外加一个显式的"记住这条"命令。

**有一件事值得让 Harness 顺手做**：一个显式的"记住这条"命令。

因为纯自动抽取永远抓不准"用户当时觉得重要"的那句话。用户按一下，直接写一条高置信度条目，跳过整条整理流水线。成本几乎为零，价值极高——它是唯一一个能把人的判断直接注入记忆的入口。

### 三个组件的职责边界

| 组件 | 该做的 | 绝对不该做的 |
|---|---|---|
| Harness 插件 | 打包、标识、入队、显式记住 | 判断什么值得记、调用 LLM 整理 |
| Worker | 触发、筛选、压缩、去重、写入 | 自己存数据、绕过 kernel 改文件 |
| 思源 | 存储、索引、展示、人工纠错 | 跑定时任务、调模型做整理 |

## 十六、思源作为存储层，够不够格

**结论：够，而且超配。但只在"元数据 + 关系"这件事上够格。**

### 它白送的六样（自己写最烦的部分）

| 能力 | 自己写要做什么 | 思源给什么 |
|---|---|---|
| **块级稳定 id** | 设计主键、保证改内容不移位 | 每个块天生一个 id，改内容 id 不变 |
| **任意自定义属性** | 设计 schema、写迁移 | `custom-*` 随便挂，加字段不用迁移 |
| **属性视图** | 做后台管理界面 | 表格视图，可筛选排序分组，人机共用 |
| **双链 / 反链** | 建图、维护边 | 引用即关系，反向自动可查 |
| **SQL 查询** | 写查询层 | 直接 `SELECT ... FROM blocks`，1-2ms |
| **全文索引** | 接 FTS、处理中文分词 | 内置，10-20ms |

这六样合起来，等于"块表 + 属性表 + 引用表 + 索引"一整套。**思源省掉的不是存储空间，是元数据建模——那是最烦、最容易做错的部分。**

### 它缺的四样，但都不是存储层的活

| 缺什么 | 该谁补 |
|---|---|
| 事务（写块和写属性不是原子的） | worker：内容哈希 + 先查后写，保证幂等 |
| 向量检索 | worker 或插件，外部索引对齐块 id |
| 调度 / 触发器 | worker |
| 版本 / 审计 | worker 或 git 快照 |

### worker 要额外小心的两个坑

**写入非原子。** 一条记忆 = 建块 + 设属性两步，中间失败就是半条。必须靠"先写属性再写内容"或"写完校验"兜住，不能指望存储层回滚。

**属性视图的 API 比普通块绕。** 属性视图本身是 `av` 类型块，读写要走专门接口，SQL 查法跟普通块不同。第一次接会卡。

### 关于 OpenViking 的判断（保留意见）

没读过它的源码，不敢断言。从外部行为倒推（记碎、召回怪、没看到任何引用关系），它更像"文件分层 + 向量索引"，没有块级 id、没有属性表、没有关系边。

如果这个推测成立，那它的问题恰恰是**只做了存储，跳过了元数据建模**——而这正是思源白送的那部分。

### 一个定位上的修正

worker 不是"在思源之上"，是"在思源旁边"。

它不扩展现有系统，它是思源的**写入客户端**。这个定位很重要：决定了两者可以各自独立升级，思源换版本、worker 换逻辑，互不牵连。

**一句话：思源解决"存和查"，worker 解决"写什么、什么时候写"。分工干净。**

## 十七、OpenViking 源码结论：能抄什么，不能抄什么

看了 `volcengine/OpenViking`（41k 星，Rust + Python，5458 个文件）。结论：**你猜得基本对，它确实是"文件堆叠 + 向量 + rerank"。**

### 存储真的就是文件

- 内容层叫 AGFS，已经重写成 Rust 的 RAGFS，**POSIX 文件操作**（read/write/mkdir/rm/mv）
- `viking://resources/docs/auth` 只是映射到 `/local/{account}/resources/docs/auth` 的 URI 壳
- 索引层独立：存 URI + 向量 + 元数据 + abstract
- 官方文档自己写：**"FS 是事实来源，VectorDB 是派生索引"**

### 但有两处比"文件堆叠"讲究，值得抄

**一、L0/L1/L2 三级抽象**

| 层 | 名称 | 存哪 | 字数上限 | 用途 |
|---|---|---|---|---|
| L0 | Abstract | 目录下 `.abstract.md` | 256 字 | **向量检索** |
| L1 | Overview | 目录下 `.overview.md` | 4000 字 | **rerank**、导航 |
| L2 | Detail | 原始文件 | 无限 | 按需加载全文 |

这是为省 token 设计的：向量只在 256 字的摘要上算，重排只看 4000 字的概览，全文永远不参与排序。**很实用。**

**二、rerank 挂在 L1 上**

候选的概览喂给重排模型，比拿整段正文去重排便宜一个数量级。这是工程上的合理取舍。

**但注意一个关键设计**：L0/L1 是**目录级**的，不是每个内容块都有。文件摘要只是聚合进所属目录。所以它的语义粒度是"目录"，不是"记忆单元"——**东西随便丢进几个目录，L0/L1 就粗得没用**。

### 两个致命弱点，文档自己承认

**一、排序不看时效**

> "Scores and ranking use rerank scores when available, otherwise vector scores; **access frequency, update time, and parent-directory scores do not affect them.**"

这就是你说的 Oracle 问题：三个月前被否掉的方案和今天的最终决定，在排序里**同权**。它只有向量分和重排分，没有任何时间、频次、状态信号。

**二、多查询合并不去重**

> "Merged results may exceed it, and the current implementation **does not guarantee deduplication across queries**."

意图分析会生成多个 TypedQuery（MEMORY / RESOURCE / SKILL），每个各查一遍，结果合并时可能重复。

### 还有一条设计哲学，值得记住

> **"Better to miss a search result than to return a bad one."**（宁漏不错）

它跨 FS、VectorDB、Queue 没有原子事务，只有路径锁和持久队列补偿。所以它选择宁可漏，不可错。这个取舍对记忆系统是对的。

## 十八、向量和 rerank 能不能搬到思源

**不能加进思源，但能加在 worker 里，而且比它更好做。**

### 为什么更好做

| OpenViking | 思源 + worker |
|---|---|
| 主键是 `viking://` URI，移动目录会变 | 主键是块 id，改内容不变 |
| L0/L1 要 LLM 生成，存成 `.abstract.md` | 文档块天然是 L1，段落块是 L2，**条目块的一句话结论天然是 L0**，不用生成 |
| FS 和 VectorDB 两套，没有原子事务 | 写入是单点（worker），索引跟着写，天然一致 |
| 排序没有时效和状态 | SQL 里加 `状态='current'` 和按时间排，一行的事 |

### 具体怎么加

**索引**：`sqlite-vec`（单文件、零部署）或 LanceDB。key 用块 id。

**embedding**：`bge-m3` 或 `bge-small-zh`，本地 onnx，几百 MB。写入时顺手算，不进主流程。

**rerank**：`bge-reranker-v2-m3` 本地，或走 API。只在候选 20 条上跑（不是全库），单次几十到几百毫秒。

**检索链路改成这样，跟它反过来：**

```
用户查询
  ↓
① 结构化过滤：状态=current + 实体/类型 + 时间窗口   ← 这一步它没有
  ↓  候选通常剩 5-50 条
② 向量排序（在 L0 摘要上算）                        ← 抄它
  ↓  取 2×limit
③ rerank（在 L1 概览上算）                          ← 抄它
  ↓
④ 终排：rerank 分 × 置信度 × 时效分                 ← 这一步它也没有
```

**关键差别在①和④。** 向量和 rerank 解决的是"找得到"，解决不了"哪个还有效"。后者靠状态过滤和时效排序，而这正是思源最擅长的部分——SQL 一句话。

### 顺序不能反

**先跑通①，再上②③。**

没有状态过滤的向量检索，就是 OpenViking：找得到一堆，但分不清哪个还算数。先把"当前有效"这件事做对，向量才有意义。反过来做，你会得到一套更快、但同样吵的系统。

### 什么时候值得上

判断标准就一条：**记录漏召回的查询，看答案在不在库里。**

- 在库里但没搜到 → 上向量
- 根本不在库里 → 改写入规则，上向量白搭

先跑两周再决定。以你现在的数据量（301 篇文档、4 万块），关键词 + 结构化过滤能撑很久。

## 十九、DSH 插件怎么写（官方文档 + 本机实查）

### 三件套：插件 / 组合包 / profile

- **插件**：一个 npm 包，入口导出 `name` 和 `apply(ctx)`
- **组合包（bundle）**：`package.json` 里声明 `dsh.bundle.patch`，指向一个 `cordis.patch.yml`
- **profile**：`$DSH_HOME/profiles/<名字>/`，`package.json` 里声明 `dsh.profile.bundles`，列出按顺序叠加的包

启动时按顺序叠：profile 里每个 bundle → profile 的 `cordis.patch.yml` → home 级 patch → `--patch` 覆盖。

### 官方最小插件（6 行）

```js
export const name = 'hello'
export function apply(ctx) {
  console.log('[hello] loaded')
}
```

`package.json`：

```json
{
  "name": "dsh-hello-plugin",
  "version": "0.1.0",
  "type": "module",
  "main": "index.js",
  "files": ["index.js", "cordis.patch.yml"],
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

`cordis.patch.yml`：

```yaml
- insert:
    - id: hello
      name: dsh-hello-plugin    # 必须是包名，不能写相对路径
```

安装 / 验证：

```bash
dsh plugin --profile desktop add ./dsh-hello-plugin
dsh --profile desktop --dump-config     # 打印实际启动的配置树
```

`--dump-config` 这一步很重要：**任何它打印出来的条目，都能被你的 patch 覆盖。** 这是排查"插件装了但没生效"的唯一可靠手段。

### 本机实查

- 桌面版在 `/Applications/DeepSeek Harness.app`，profile 在 `~/.dsh/profiles/desktop`
- **`desktop` 是 Electron 保留的 profile**，由应用自己管，别手改坏
- 已装：`@openviking/dsh-memory-plugin`、`@xmanrui/dsh-im`、`dsh-skill-mcp-panel`
- 底层是 **cordis**（Koishi 那套）：`ctx.on(事件)` / `ctx.provide(服务)` / `ctx.effect(清理)`，注册都是可逆副作用

### 可挂的生命周期事件

从本机那个 973 行的 OpenViking 插件里观察到（非官方文档，需以 `--dump-config` 或类型定义为准）：

`agent/created`、`agent/session-start`、`agent/pre-step`、`session/event`、`session/flush`、`tools/pre-execute`、`tools/post-execute`

我们要用的只有两个：`agent/pre-step`（注入）、外加一个显式命令（记住这条）。

### 坑：会话日志是多帧 zstd

`session.v4.jsonl.zstd` 是追加写的，**每一段是一个独立的 zstd 帧**。

用 Node 内置的 `zlib.zstdDecompressSync` 只能解出**第一帧**——实测一个 0.9MB 的文件只解出 243 字节、一行。必须用支持多帧的解码器（`zstd` CLI、或库里的 streaming 接口），否则读到一半就断，而且不报错。

这个坑很隐蔽：解压"成功"了，只是内容少得离谱。

## 二十、职责边界：谁做什么，别含糊

### 采集：插件不做，worker 只做"增量追赶"

不做"会话结束"这个事件。理由：日志是追加的，worker 记录**已读偏移**，每次只处理新追加的帧。会话还在写也能处理已写部分，剩下的下次补。

这样有两个好处：

- 不需要判断"结束"，不用等超时，不用插件打标记
- 崩了不用重来，偏移量就是进度

偏移要按**帧**记，不是按字节（多帧 zstd 的字节偏移在重写时会漂）。

**何时跑**：`mem serve` 常驻时每 10 分钟扫一次；或者手动 `mem once`。插件完全不参与。

### 日志里有什么，必须怎么过滤

官方说日志记了模型看到的一切：system prompt、thinking、工具调用与结果、子代理派发、上下文注入。

**硬过滤规则：**

| 类型 | 处理 | 原因 |
|---|---|---|
| `user` 的文本 | **保留** | 这是唯一的人类输入 |
| `assistant` 的最终文本 | **保留** | 这是结论 |
| `assistant` 的 thinking | 丢弃 | 过程，且大量是被否定的方案 |
| `tool_call` / `tool_result` | 丢弃 | 结果已在磁盘上，过程不可复用 |
| system prompt | 丢弃 | 每次一样，没有信息量 |
| 子代理事件 | 丢弃 | 噪音 |
| **我们自己注入的上下文** | **必须丢弃** | 见下 |

### 自我污染：这套设计里最容易翻车的地方

注入的记忆会出现在日志里。如果抽取时不排除，第二轮就会把"上次注入的记忆"当成"用户说的话"再抽一遍，第三轮再抽一遍——**记忆自己喂自己，越滚越脏，而且看不出源头**。

两条防线：

1. **注入时打标记**。DSH 的 `createUserMessage` 支持 `source: { kind: "plugin:siyuan-memory", plugin: "siyuan-memory" }`。模型看得见内容，日志能认出这是插件塞的。
2. **抽取时按 `source.kind` 前缀 `plugin:` 全部丢弃。**

这两条必须成对出现。只做第一条，标记白打；只做第二条，会误伤真正的用户消息。

### 四个职责，划清楚

| 组件 | 只做这些 | 一行都不做 |
|---|---|---|
| **DSH 插件**（~60 行） | `agent/pre-step` 首次注入；注册一个"记住这条"命令 | 采集、整理、查询 |
| **`mem mcp`**（同包，stdio） | 暴露 `search` / `remember` / `forget` / `review` 四个工具 | 自己的存储 |
| **`mem once` / `mem serve`** | 读日志、过滤、抽取、去重、写思源 | 提供 UI、自己存数据 |
| **思源** | 存、索引、展示、人工改 | 调度、调模型 |

三个子命令是**同一个包**：`mem mcp` / `mem once` / `mem serve`。不是三个项目。

### 查询为什么走 MCP 而不是插件里写工具

- 插件里写工具要自己处理 schema、参数校验、错误返回，几十行起步
- MCP 是 DSH 原生支持的能力（本机那个 OpenViking 插件就是靠它挂工具的）
- **跨 harness 复用**：同一个 MCP server，Claude Code、Cursor、DSH 都能接，插件不用各写一遍

所以查询不进插件。插件只管"开机给模型看几条"，查询让模型自己调工具。

### 注入协议

| 项 | 定 |
|---|---|
| 时机 | `agent/pre-step`，**仅首次**（同一个 agent 只注入一次） |
| 条数 | 5-10 条 |
| 预算 | 硬上限 800 字，超了截断，不"差不多" |
| 位置 | 作为带 `plugin:` 标记的用户消息，不塞 system prompt |
| 格式 | 结构化列表，每条带日期和状态 |
| 去重 | 与本次会话已注入过的比对，不重复塞 |

**为什么不塞 system prompt**：system prompt 里的内容模型当规则，记忆是背景。混在一起，模型会把三个月前的偏好当成硬性指令执行。

### 一句话总结这套分工

**日志是事实，worker 是过滤器，思源是仓库，MCP 是查询口，插件只是开机时递一张便条。**

## 二十一、现成件能参考到什么程度

查了一圈，结论是：**"怎么接"和"怎么写插件"全部有现成答案，"记什么"没有一个人做。**

### 可以直接拿来用的（零代码）

| 东西 | 提供什么 | 用法 |
|---|---|---|
| 思源 MCP server | 30 个工具：block / attr / database / document / search / sql / ref / tag | DSH 配一个地址即可读写，`127.0.0.1:6806/mcp` |
| 思源 CLI | 30+ 子命令，带 `--dry-run` | 人和 agent 现敲；程序内部不用它（150ms vs 7ms） |
| 思源内置 AI agent | 34 个能力，含 `decision` 批量打分、`skill`、`todo_write` | 配了模型才能用；能不能替代 worker 见下 |

### 源码可以照着抄的（该抄哪一处）

**`LuoX218/dsh-siyuan`**（npm `dsh-siyuan-sync`）——手动同步，但三处值得抄：
格式映射（LaTeX / mermaid / 代码块 / 表格 / 任务列表 → 对应块类型）、本地队列、写入前预览。
它证明了一件事：DSH 里拿到对话内容并落成思源块，这条路是通的。

**`terwer/dsh-siyuan-note`**——走原生 CLI + skill。安全设计比功能更值得抄：
改完自动 pull/push、破坏性操作先 dry-run、真实空间默认只读。这三条要照搬。

**`@openviking/dsh-memory-plugin`**（就装在你 profile 里，973 行）——DSH 插件的活样板：
`agent/created`、`agent/pre-step`、`session/event`、`session/flush`、`tools/pre-execute/post-execute` 的用法，
外加一套 pending queue + drainer。我们的插件骨架可以从它删到 60 行。

**OpenViking 的 L0/L1/L2**——省 token 的三级抽象。思路可抄，实现不用：
在思源里，文档块天然是 L1、段落块是 L2、一句话结论天然是 L0，不需要 LLM 生成摘要。

**DSH 官方插件三件套**（`package.json` 的 `dsh.bundle.patch` → `cordis.patch.yml` → profile 叠包）
——这个不是参考，是必须遵守的规范，写错了装不上。

### 抄不了的（这就是自己的活）

三件事，所有现成件都止步在这里：

**一、判断"哪句值得记"并压成一句。**
它们存的是整段对话；我们要的是一条带实体名的结论。

**二、状态机。**
`current` / `superseded` / 衰减。没人做，因为这是"记忆"和"归档"的分界。

**三、无人时的调度。**
思源 agent 要人开窗口，MCP 是被动的，插件绑在进程上。定时这件事只能外面做。

### 一个判断：要不要直接用思源内置 agent 干整理

它的 `decision` 能做批量分类和打分，`document`/`block` 能改块，`web_search` 能查外部，
配上模型之后，理论上"读一批归档 → 提炼成条目 → 写进笔记本"它能自己做。

所以 worker 有可能缩到只剩：**定时触发 + 把日志过滤成问答对 + 调 `/api/ai/agent/chat`**。

但这有个代价要先算：它会把你归档的原文发给模型商，而且是每次整理都发。
另外 agent 的产出格式不稳定（它是对话式的，不是 JSON），要写解析和校验。

折中方案：**worker 自己调一个便宜模型的 API，只做"压成一句话 + 填实体名"这种窄任务**，
不用思源 agent。窄任务用结构化输出，成功率接近 100%，也不依赖思源的 AI 配置。

第一版就这么做。等真跑顺了，再评估要不要把整理交给思源 agent。
