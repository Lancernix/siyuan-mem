# 用思源笔记做 DSH 的原生知识库 / 记忆后端

写于 2026-10-28。前提：DSH = DeepSeek Harness，本机思源桌面端在跑，kernel API 可用（已验证 `blocks` 表可查）。

---

## 一、结论

能做，而且对你是对的选择。但要把预期摆正：

**这件事 20% 的功夫在"存哪儿"，80% 在"写什么、什么时候写、什么时候拿出来"。**

换存储救不了记忆系统的质量问题。OpenViking 让你觉得一般般，大概率不是它存得不好，是它的写入和召回策略不匹配你的用法。思源也一样，光把后端换过去，结果不会更好。

思源真正值钱的地方，不是"可控"，是**你每天都在那儿读**。写错的条目你会看见，会顺手改掉。黑盒向量库写错了没人知道，错误会一直累积下去。这个纠错回路，比任何检索算法都值钱。

---

## 二、先纠正一个前提

你说"思源也是 Markdown 的形式"，这句话只有一半对。

**落盘不是 Markdown。** 思源的数据目录里是 `.sy` 文件，块级 JSON 树，不是纯文本 md。所以：

- 不能像 Obsidian 那样直接用编辑器改文件，改了索引对不上，块 id 会漂。
- 一切读写必须走 kernel API（`/api/...`，token 鉴权，默认 127.0.0.1:6806）。
- 所谓"可控"，是**API 层面可控**（SQL、块属性、属性视图、引用关系都能查能改），不是文件层面可控。

这个区别很实际：它决定了插件不能"离线写文件、下次启动再同步"，只能依赖思源进程活着。掉线要有降级方案。

---

## 三、思源适合做记忆库的三个真实优势

**1. SQL over blocks。** 块可以挂自定义属性（`custom-*`），然后直接 `SELECT ... FROM blocks WHERE ...`。等于免费得到一个可查询的结构化索引，不用自己搭数据库、不用自己维护 schema 迁移。

**2. 属性视图（数据库）。** 这是记忆索引表最合适的形态：一行一条记忆，字段自己定。人在思源里能直接看、直接改、直接筛，机器用 SQL 读。人和 agent 共用同一张表——这是别的方案给不了的。

**3. 块引用即图谱。** 记忆条目之间用块引用连起来，天然有双向链接，不用单独建图数据库。

---

## 四、思源不适合 / 要自己补的

**没有向量检索。** 思源的搜索是分词 + 关键词，不是语义。记忆召回最怕"意思对但词不对"，比如你记的是"投影仪桌面已经换成自己写的"，问的是"电视启动器现在什么状态"，关键词可能对不上。

补法：外部小向量索引（sqlite-vec 或 LanceDB），key 用思源块 id 对齐。**但 v1 别上**，先用 SQL 过滤 + 关键词，跑两周看漏召回率，真不够再加。

**写入有成本。** 每次写都过 kernel，触发索引更新。如果每轮对话都写，几十次之后会明显拖慢。所以写入必须批量化，挂在会话结束和压缩点，不能逐轮写。

**依赖进程存活。** 思源关了就没了。降级方案：本地留一个 append-only 的 jsonl 兜底，启动时补偿写入。

## 五、架构：两层 + 四个钩子

### 两层

- **热层**：当前会话的工作记忆，留在插件进程内存里，不落盘。会话结束才落。
- **冷层**：思源，长期存储。一个实体一条文档，外加一张属性视图做索引。

### 四个钩子点（这也是选框架的依据）

| 时机 | 动作 |
|---|---|
| 会话开始 | 召回：按分数取 Top N，注入上下文，硬性字数上限 |
| 压缩前（PreCompact） | 落盘：把这一段的决策、偏好、结论抽出来写进思源 |
| 会话结束 | 整合：去重、合并、更新衰减分 |
| 工具调用前（可选） | 机会性召回：命中特定关键词时补一条相关记忆 |

这四个点，Claude Code 的 hooks 全有，DSH 的插件层能在进程内做（比 shell 出去调脚本干净），WorkBuddy 只有工具调用，生命周期钩不到。

**所以你的判断对：要做自动化，框架必须能挂生命周期，不只是能调 API。**

## 六、数据模型

一张属性视图，字段：

| 字段 | 说明 |
|---|---|
| 实体 | 这条记忆说的是什么（投影仪桌面 / 风盾500 / DSH 插件） |
| 类型 | 决策 / 偏好 / 事实 / 教训 / 待办 |
| 内容 | 一句话，不超过 60 字 |
| 置信度 | 1-5，用户明确说过的是 5，推断的是 2 |
| 来源 | 会话 id + 日期 |
| 最后使用 | 上次被召回的时间 |
| 衰减分 | 由时间和使用次数算出来，用于排序 |
| 状态 | 有效 / 已废弃 |

**关键一条：一条记忆一个块，不要一篇文章塞十条。** 否则去重、衰减、引用全都做不了。

---

## 七、写入策略（最容易做砸的地方）

**不要逐轮抽取。** 每轮对话都写，会产生大量"今天用户问了 X"这种垃圾条目，三个月后整个库全是噪音。

**只在三个时机写：**
1. 一个话题明确结束（用户说"就这样"、"定了"、"下一个"）
2. 上下文要压缩了
3. 会话结束

**写之前先去重。** 按实体名做 key，查已有条目：
- 已有且不冲突 → 只更新"最后使用"和置信度
- 已有但冲突 → 旧条目标"已废弃"，新条目加"取代了 xxx"的引用
- 没有 → 新建

**不该写的：** 一次性的操作细节（"我把 paddingTop 改成 212dp"）、能重新推导出来的东西、情绪性的表态。

**该写的：** 用户的偏好（"他不喜欢磁贴有常驻透明壳"）、做过的决策和理由（"选了 500 不选 300，因为膝盖弹力是结构性问题"）、踩过的坑（"按包名排除桌面会把设置一起干掉"）。

---

## 八、召回策略

**排序公式：** 相关度 × 置信度 × 衰减分，取 Top N。

**衰减：** 每次被召回，分加回来；超过 90 天没被召回且置信度低于 3 的，进"沉降区"，不再默认注入，但仍可搜到。

**注入预算：** 硬上限。会话开始最多 800 字，机会性召回每次最多 200 字。没有预算控制的记忆系统会吃掉所有上下文。

**召回失败要记录。** 哪些查询没命中，就是下一批该补的记忆类型。

---

## 九、v1 范围（别做大）

只做三件事，两周能跑起来：

1. 会话结束 → 抽取 3-8 条记忆 → 去重 → 写进思源（一个独立笔记本，别混进现有笔记）
2. 会话开始 → SQL 查属性视图，按分数取 Top 10 → 注入
3. 手动命令：`/memory search xxx`、`/memory forget xxx`、`/memory review`（列出最近写入的，方便你纠错）

**v1 不做：** 向量检索、自动衰减（先按时间粗略算）、多 agent 共享、跨设备同步。

第 3 条里的 `/memory review` 是重点。没有人工复核入口，这个库三个月就烂掉。

---

## 十、坑

**笔记本要独立。** 别写进"09-每日复盘"或"06-算法"，会污染。单独建一个，名字带前缀，比如 `99-记忆`。

**属性视图是块，不是表。** 它的数据在 `blocks`/`attributes` 里查，SQL 写法跟普通表不一样，要按块属性查。第一次接的时候会踩。

**中文分词。** 思源对中文分词还行，但对专有名词（`风盾500`、`DSH`、`fuwu`）容易切碎。写记忆时把关键词一起放进块属性，比依赖全文搜索可靠。

**写入要幂等。** 插件重启、重复触发都可能写两遍。每条记忆带一个内容哈希，重复的直接丢。

---

## 十一、备选方案对比

| 方案 | 优势 | 劣势 | 适不适合你 |
|---|---|---|---|
| **思源** | 你每天在读，纠错回路天然存在；SQL + 属性视图省掉自建索引；本地、免费 | 无向量检索；依赖进程；`.sy` 不是 md | **适合**，纠错回路这条最重要 |
| Obsidian + Dataview | 插件生态好，md 纯文本 | 没有服务端 API，agent 要么改文件要么走 URI，写入很别扭 | 不适合 |
| SQLite + md 文件 | 最简单，完全可控，无依赖 | 你自己不会去翻，写错了没人发现 | 只适合纯机器用 |
| OpenViking 这类现成的 | 装上就能用 | 写入和召回策略不可调，跟你用法不匹配 | 你已经试过了 |

---

## 十二、最后一句

这件事的价值不在"多一个记忆插件"，在于**你的笔记库和 agent 的认知合成一个东西**。

现在的情况是：写文章那套在思源里，投影仪那套在会话里，骑行的装备知识又在别的地方。三个孤立的知识岛。接上之后，你问"我那套骑行装备配投影仪那个桌面还有没有别的可以调"，它能同时摸到两边。

这才是理由。存储本身不值得折腾。
